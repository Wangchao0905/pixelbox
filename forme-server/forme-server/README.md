# forme-server

Pixel Box 微信小程序的后端服务。零运行时依赖（只用 `node:http` + `node:crypto`），Node 20+。

完整接口契约见 **[API.md](./API.md)**。
部署到服务器见 **[DEPLOY.md](./DEPLOY.md)**（含 systemd / Docker / nginx 配置与上线检查单）。

---

## 快速开始

```bash
# 1. 配置（可选。默认就是 mock 模式，不填也能跑）
cp .env.example .env.local

# 2. 启动
npm start

# 3. 自测
npm run smoke        # 端到端冒烟，287 项断言
npm run check:holds  # 孤儿预扣回收（会真的杀进程，13 项断言）
npm run preflight    # 上线前自检（部署到服务器后跑）
npm run check:adversarial  # 对抗测试 preflight 的门禁（会临时改源码，故不在 check 里）

# 4. 封面图（把小程序里的远程封面收到自有域名下，见 DEPLOY.md 9.2）
npm run fetch:covers
```

默认 `MOCK_WECHAT=1` + `MOCK_LLM=1`，**不需要任何微信凭据或图片模型 key** 就能跑通全流程：
登录、生成出图（返回本地生成的占位图）、扣费、充值、发货、退款。

```bash
curl http://127.0.0.1:8787/api/health
```

`problems` 非空时进程会直接拒绝启动，把「会导致线上事故但不会立刻报错」的配置挡在启动阶段。

## 三个关键设计决定

### 1. 扣费顺序：预扣 → 结算 / 回滚

不是「先调用，成功再扣」：

```
先扣后调：上游失败要回滚，回滚失败会多扣用户的钱，但不会超扣。
先调后扣：并发下两个请求可能同时通过余额校验，双双生成后一起扣，
         余额被扣成负数 —— 这是真正赔钱的 bug。
```

所以余额校验与扣款在**同一次同步写**里完成（`reserveCharge`），上游失败再还回去。
宁可偶发多扣（有流水可查、可补偿），也不要超扣（用户白拿）。

这条不变量的测试覆盖在 `scripts/smoke.mjs` 的第 21、22 节：一个 `INITIAL_BALANCE=4`
（刚好够 1 张图）且上游不可达的隔离实例，专门压余额边界与回滚。

### 2. 发货依据：平台查单，不是客户端回调

用户支付后异常退出会丢 `success` 回调，拿回调当发货依据 = 漏发货。

```
/pay/notify  平台推送 → 按 Event 分发 → 幂等 → 处理 → 回 XML
/pay/query   兜底查单（前端轮询 + 定时任务扫未发货订单）
```

推送先验消息签名，发货再查平台订单。查单签名 `pay_sig` 放在 URL 查询参数中，
读取 `order.status`，仅接受 2/3/4，并核对订单号、金额、环境和平台单号。
查单补发后调用 `notify_provide_goods`；确认失败会持久记录并定时重试，不重复加点。

**发货必须是单次原子写入**：点数到账 + 发放权益 + 改订单状态，三件事收在
`store.settleOrder` 的一次 `mutate()` 里。拆开写的话，进程在中间崩掉会留下
「订单仍 pending 但点数已加」的状态，平台重试就会重复加点。

### 3. 退款通知校验与回收

退款推送先验消息签名，再核对退款成功状态、订单号、用户、平台单号和全额退款金额。
任一字段不匹配都不回收点数。回收下限为 0（用户可能已消费），收不回来的部分
记为 `shortfall` 并主动告警。当前只处理全额退款，部分退款需单独设计点数比例规则。

### 4. 定价：售价不变，套餐点数预留渠道费，单张图 0.4 点

点数单价由 `IMAGE_COST`（默认 `0.4`）决定，新用户初始余额由 `INITIAL_BALANCE`（默认 **`0`**）决定。
两者都在 `.env` 里，改价不需要重新发版 —— 客户端一律以 `/api/catalog` 返回的 `imageCost` 为准。

`IMAGE_COST` 是小数，所以**余额与流水一律按两位小数记账**（`Number(x.toFixed(2))`），
不要「为了整数好看」把它换算成整数分：那样 `imageCost` 与余额的单位就不一致了，
对账时最容易出的错就是差一个 100 倍。

三个刻意的选择：

- **不做新人赠送。** 赠点会立刻制造两类问题：批量注册刷点数的成本直接落在上游出图账单上；
  免费用户与付费用户共用同一套限流阈值时会互相挤占额度。将来真要做活动，应该做成
  **有门槛、有上限、可随时关闭**的独立通道，而不是把默认余额改成一个正数。
- **`INITIAL_BALANCE` 非法值不静默兜底。** `IMAGE_COST` 必须是 > 0 的有限数：
  填 `0` 等于出图完全免费，填非法值会把余额算成 `NaN` 且无法恢复。生产环境下
  这两种情况都会**阻止启动**。
- **「约 N 张图片」由服务端按当前单价现算**，客户端不复刻算式、不写死张数。
  这条是踩坑换来的：单价从 0.35 调走之后，写死的「约 285 张图片」还在响应里，
  而实际张数早就不是那个数 —— 文案错得越具体，用户越容易当成承诺去投诉。

`scripts/smoke.mjs` 有一个**故意不传** `INITIAL_BALANCE` 的隔离实例（`fresh`），
走的是生产默认值，专门盯住「不送点数」这条策略；谁把默认值改回非 0，冒烟立刻变红。

> **2026-09-24 调整：** 30 元 / 26 点 / 30 天；100 元 / 88 点 / 30 天；
> 100 元 / 88 点；500 元 / 440 点。按 12% 渠道费预留并向下取整，
> 每张仍扣 0.4 点，分别可生成 65、220、220、1100 张图。
> 旧订单与已有余额保持原值；1 元测试商品仍为 1 点。productId 保留历史标识。
> 这只覆盖支付渠道费，生成成本、税费及运营成本仍需另行核算，不能据此认定盈利。

### 5. 预扣（hold）是「在飞的钱」，启动时必须对账

出图的扣费是**预扣 → 上游调用 → 结算或回滚**三段（见 `image.mjs` 顶部注释）。
预扣一落盘，钱就已经离开用户余额了，此时磁盘上多出一条 `pending` 流水。

问题在于这个中间态会**跨进程存活**：进程如果在「预扣已落盘、上游还在 `await`」的窗口里
死掉（滚动发布、OOM、`kill -9` 都会走到这里），`commitCharge` 和 `releaseCharge`
都不会跑，于是留下一个**永远没人处理的 hold**：

```
用户余额被永久扣掉 · 流水停在 pending（用户看到扣费却没拿到图）· 没有任何告警
```

正常路径下测不出来：冒烟测试不会杀自己的进程，`releaseCharge` 一定会跑到，
hold 表永远是干净的。所以这条单独有一个会**真的 SIGKILL 进程**的测试：
`npm run check:holds`。

修法是启动时回收（`reclaimOrphanHolds`，在 `server.listen` 之前调用）。
**「启动时全部回收」是可以证明正确的**：hold 的生命周期完全等于一个 HTTP 请求的
生命周期，进程重启意味着上一个进程里所有在飞的请求都已经死了，所以启动那一刻
磁盘上不可能存在仍然有效的 hold —— 每一个都是孤儿。因此这里不需要按时间猜。

代价是这条推理**只在启动时成立**，所以函数里有一个 once 闸门：进程内第二次调用
直接返回 `{skipped:true}` 的无操作。这样即使将来有人把它挂到定时器上，
误用也只会变成「不做事」，而不会退掉正在生成的请求的预扣（那是用户白拿图）。

回收动作会打日志 + 发一条 `warn` 告警。**这不是「修好了就完事」的事**：
它意味着上一次进程是非正常退出的，每一次发生都在真金白银地吃掉用户余额，
需要让人看见，否则会一直发生。

### 附：包月为什么是「30 天道具」而不是订阅

微信虚拟支付的 `mode` 固定为 `short_series_goods`，`signData` 字段写死
（offerId / buyQuantity / env / currencyType / productId / goodsPrice / outTradeNo / attach），
没有任何续费字段。官方文档「Agent 注意事项」第 2 条：只做道具直购。

所以包月做成**一次性购买的 30 天有效期道具**：买一次，权益有效 30 天，到期用户自己再买。
能卖、合规，只是不自动扣款。客户端也不要写「每月自动续费」——那是做不到的承诺。

## 上线前必须处理

已经做掉的：

- ✅ **接口限流** —— 滑动窗口，出图/上传/下单按用户，登录/兜底按 IP。
  关掉它服务在生产环境会拒绝启动
- ✅ **退款缺口告警** —— 配 `ALERT_WEBHOOK_URL` 后主动推送（企业微信/钉钉/飞书）
- ✅ **内容安全切 enforce** —— 生产环境留 `log` 会拒绝启动
- ✅ **mock 接口生产不可达** —— `MOCK_WECHAT=0` 时路由根本不注册（404 而非 403）
- ✅ **启动自检门禁** —— 配置不对直接拒绝启动，不给你「先跑起来再说」的机会
- ✅ **孤儿预扣启动回收** —— 进程在结算前退出时自动把钱退还给用户，并告警
- ✅ **部署件与上线自检** —— 见 [DEPLOY.md](./DEPLOY.md) 与 `npm run preflight`

还需要做的（按优先级）：

| 项 | 现状 | 需要做什么 |
| --- | --- | --- |
| 文件存储 | 本地磁盘 `data/uploads` | 换 COS/OSS。单机够用，多实例下本地磁盘不共享 |
| 数据存储 | 单进程内存 + JSON 落盘 | 换 Postgres/MySQL，只需替换 `src/store.mjs` |
| 权益撤销 | 退款不自动撤销权益 | 若业务上需要收回，在 `store.refundOrder` 里补 |
| 定时查单 | 进程内 `setInterval` | 多实例会重复查单（有幂等保护），建议换外部定时任务 |
| 图片 CDN | `/api/files/:id` 由 Node 直出 | 换 CDN，见 `deploy/nginx.conf` 的缓存配置 |

以及 `MOCK_WECHAT` / `MOCK_LLM` 必须为 `0`，道具 `productId` 与价格要和 MP 后台完全一致
（见 API.md 第 7.6 节）。iOS 支付还需要微信 ≥ 8.0.68，并在 MP 后台配置小程序简称。

另外别忘了开通条件：**个人主体 + 服务类目含「工具」+ 已完成认证与备案**，
月支付限额 10 万元，当前费率 Android 主动支付 1%、iOS 12%（见 API.md 官方来源，以实际账单为准）。
